Parkeringsassistent P40

Security and technical safety principles

Last updated: 6 October 2026

Independent app: Parkeringsassistent P40 is not developed, approved, supported or operated by SmartPark, Trondheim Parking, Trondheim Municipality or the parking operator.

This page describes user-relevant security principles. It does not publish secrets, tokens, private keys or internal details that would weaken security.

Sign-in and credentials

  • The SmartPark session/token is stored in Apple Keychain, not ordinary UserDefaults, widget state, diagnostics or Apple Watch.
  • Phone number and SMS code are used in the sign-in flow and are not included in shared diagnostics.
  • When authentication is confirmed expired, P40 fails closed and requires sign-in again. A temporary network/restore failure while a Keychain session is still stored is not by itself treated as confirmed sign-out, and an older local sign-in warning is cleared after a later authenticated SmartPark verification succeeds.
  • After real expiry, the notification/dialog action reveals the normal phone-number sign-in form. P40 does not start the SmartPark verification page until a valid mobile number has been entered.

Network and third-party services

  • SmartPark communication uses HTTPS to a fixed expected service origin.
  • The verification page uses a non-persistent WebView and restricts the native message bridge to the expected SmartPark origin.
  • Vehicle lookup uses HTTPS through the developer's Cloudflare Worker to the Norwegian Public Roads Administration technical vehicle API. The registration number is sent by the app in the JSON body of an HTTPS POST request, not in the Worker URL. The API key is not embedded in the app.
  • P40 depends on third-party services and can stop working if their API, policy or access changes. Unknown/changed responses are intended to fail closed rather than be guessed around.

Parking booking and stopping

  • P40 checks existing P40 status before a new booking and does not blindly retry writes after an uncertain result.
  • A destructive stop is bound to the expected vehicle and exact active SmartPark permit.
  • P40 does not automatically stop an unused scheduled parking session. After safety checks the app may offer Keep parking or Release parking. DELETE is sent only after the user's explicit choice and a fresh active-parking verification.
  • If status, authentication, network, GPS or permit identity is uncertain, the parking session is kept.

Automation and location

  • P40 Start is the scheduled action. Optional P40 Arrival Start uses the user's Apple Shortcuts Arrive trigger.
  • P40 Arrival Start does not perform a second native 1 km GPS gate before booking. P40's own 1 km region is post-booking safety evidence for a relevant scheduled booking.
  • P40 keeps the latest automatic attempt, its outcome and the last confirmed automatic parking start separate. An attempt made while parking is already active is recorded as not started and does not change confirmed-start history.
  • The latest automatic-attempt outcome is stored locally as language-independent status used only for presentation and diagnostics; it does not grant authority to book or stop parking.
  • Location is processed locally. GPS coordinates are not sent to SmartPark, the developer or the vehicle-lookup service by this feature and are not stored as parking history.
  • Boundary uncertainty fails closed: P40 must establish that even the closest plausible position is outside 1 km before Release parking can be offered.

CarPlay, widget and Apple Watch

  • Widget and Watch do not receive the SmartPark token, SMS code or phone number.
  • The CarPlay widget may show Book for vehicles the user explicitly enabled for P40 in CarPlay when local status is confirmed missing. An exact audio/connection-name match is not a security factor.
  • Book/Release from the widget opens the main app. The main app performs fresh SmartPark, vehicle and safety verification before any write/DELETE.
  • The user can mask the registration number on Lock Screen, Dynamic Island, Apple Watch and CarPlay/StandBy surfaces.
  • App startup no longer ends a possibly valid Live Activity before SmartPark status is known. Confirmed active P40 updates or restores Live Activity; confirmed non-active P40 removes it.
  • If ActivityKit rejects the full Live Activity presentation with the optional local vehicle photo, P40 may retry once without the image. This is presentation-only and never triggers a parking booking or DELETE.

Diagnostics and on-device AI

  • Diagnostics are never sent automatically to the developer.
  • Known registration numbers are masked before diagnostics are copied, shared or used by the optional AI explanation.
  • The AI explanation uses Apple Foundation Models on-device when available and is clearly labelled AI-generated. AI output does not confirm valid parking.
  • The AI model is instructed to use natural wording in the selected language and to distinguish clearly between started, not started, blocked, failed and uncertain outcomes without inventing new facts.
  • Interface translation uses Apple Translation on-device. That API does not expose a separate system-prompt field, so P40 uses short, explicit and context-rich source text to improve translation quality.
  • An older error is labelled historical/resolved when a later authenticated SmartPark check succeeds.
  • Session diagnostics may locally store counters/timestamps, a coarse endpoint label, HTTP status and whether an X-Token header was observed or actually rotated. The token value itself is never written to diagnostics and remains Keychain-only.
  • P40 does not add or guess an undocumented SmartPark refresh endpoint.
  • Live Activity diagnostics may store a local timestamp/result for creation, update or fallback. This introduces no new external data sharing.
